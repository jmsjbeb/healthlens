# 康鉴 HealthLens · 体检报告解读与健康改善计划

一个把「体检报告」翻译成「我该做什么」的产品。

上传报告 → 分清真假异常 → **按星级排先后** → 判断哪个科必须去、哪个不用去 → 一份「怎么吃」、一份「怎么运动」，都细到能照着做。

> **在线版** <https://jmsjbeb.github.io/healthlens/> ｜ **源码** <https://github.com/jmsjbeb/healthlens>
> 觉得「判定不交给模型」这套分工有用，欢迎在仓库点个 star，或提 issue 挑一个判错的指标。

## 快速开始（接着开发用）

零依赖、零构建：clone 下来直接打开 `index.html` 就能用，断网也行。

```bash
git clone https://github.com/jmsjbeb/healthlens.git
cd healthlens
# 若 github.com 主站 HTTPS 不通（当前这台机器就是），改走 SSH over 443：
# git clone ssh://git@ssh.github.com:443/jmsjbeb/healthlens.git
# 直接双击 index.html；或起本地服务（PWA 的 Service Worker 需要 https / localhost）
node server/dev.js          # 可选，监听 8787，同时提供 AI 影像结构化的本机代理
```

> 开发机上的 `outputs/healthlens/` 是早期用 Git Data API 逐个文件推上去的工作区，**本地 git 历史与仓库不同步**，
> 别在那份目录里直接 `git push`。要长期接着开发，重新 clone 一份干净的最省事——仓库里的源码、脚本、文档是完整的。

想在本机启用 AI 影像结构化，自己新建两个**已被 gitignore** 的文件：`server/key.local.txt`（第一行写密钥）和 `js/config.local.js`（`window.HL_CONFIG = { llm: { proxy: true, model: 'glm-4-flash' } };`）。公开仓库里没有这两个文件，也不含任何密钥；不配它们，产品照常可用，影像描述保持原文。改哪个文件、脚本加载顺序见 [`HANDOFF.md`](./HANDOFF.md)，安卓打包见 [`APK.md`](./APK.md)。

## 二、四个产品判断

### 0. 「直白」的前提是给依据

首页最初写的是「把标红项讲清楚」「直接告诉你不用管」。这两句话有风险：**在医疗语境里，「不用管」是一个结论，不是一个解释。** 无条件地下结论，等于用一句口号换用户的信任；一旦某条判断错了，整个产品的可信度就没了。

改成现在的写法：**先摆证据，再下判断。**

首页放了三行红字做对照——HDL 1.50 ↑ 和 RDW-CV 11.6 ↓ 都标红，但都不用管；Hcy 19.5 ↑ 超出上限 30%，必须管。三条并排放在一起，「标红 ≠ 有病」这句话就不用解释了，用户自己看得出来。每一条后面都写了为什么（好胆固醇反向转运、RDW 只关心升高、Hcy 刺激血管内皮），并且这些依据都能在报告或公开指南里核到。

对应的文案改动：

| 原表述 | 现表述 | 为什么改 |
| :-- | :-- | :-- |
| 把标红项讲清楚 | 把每个标红项说明白 | 「讲清楚」是承诺结果，「说明白」是承诺过程 |
| 直接告诉你不用管 | 每条结论都写了依据，可以对着报告逐条核对 | 把可验证性交给用户，而不是要求用户相信 |
| 告诉你哪个科不用去 | 哪个科可以先不跑 | 不给「不用去」的绝对判断，给「先不跑、复查时再看」的时序建议 |

**结论：能直白，但不能无条件直白。** 直白的对象是判定（这一项要不要管），不是资格（你有病没病）。

### 1. 分清真假异常（最容易制造焦虑的地方）

体检报告最常见的伤害不是漏诊，是**制造焦虑**。机器会给一堆项标红，其中相当一部分临床上没有意义。

| 项目 | 报告标记 | 真相 |
| :-- | :-- | :-- |
| 高密度脂蛋白 1.50（上限 1.42） | ↑ 偏高 | 好胆固醇，偏高是保护性的，无需干预 |
| RDW-CV 11.60（下限 12.2） | ↓ 偏低 | 说明红细胞大小均匀，无病理意义 |
| RDW-SD 39.50（下限 41.2） | ↓ 偏低 | 同上 |

反过来还有一种更隐蔽的情况：**报告小结说「未见明显异常」，但数值本身不达标**。样板报告里「矫正视力右 0.6 / 左 0.7」，小结写的是「未见明显异常」，而矫正视力常规应达 0.8 以上。引擎会把这条标为「建议观察」并指向眼科——纯靠读小结读不出来。

### 2. 星级：告诉用户「先做哪件」

7 星制，7 = 最优先。**星多不代表病重，代表现在最该动手。** 排序同时看四件事：

1. 数值偏离幅度（超上限多少）
2. 器官层面是否已出现改变（只有数值 vs 已有影像/结构变化）
3. 是否与其他异常构成组合风险
4. 现在干预还来不来得及

样板报告的排序结果：

| 星 | 项目 | 为什么是这个星 |
| :-- | :-- | :-- |
| ★★★★★★★ | 同型半胱氨酸 19.5 | 超上限 30%，独立心血管风险因子，叠加脂肪肝/超重/家族史；但对补叶酸反应最好——风险和收益都最大 |
| ★★★★★★ | 脂肪肝 | 已有器官层面影像改变，但肝功全正常，正处可逆窗口 |
| ★★★★★★ | 甲状腺结节 TI-RADS 3 类 | 结节风险仅 2%，真正的疑点是「回声欠均匀」可能提示桥本，且甲功未查 |
| ★★★★★ | 超重 BMI 26.78 | 本身不算重，但它是脂肪肝与 Hcy 升高的共同土壤 |
| ★★★★★ | 肺功能 FEV1/FVC 71% | 卡在诊断临界必须排除，但 FVC 107% 提示可能是测试误差 |
| ★★★★ | 淋巴细胞升高 | 轻度异常，多为病毒感染后恢复期，先复查 |
| ★★★★ | 甲功缺项 | 不是异常是缺失，但卡住了甲状腺那条线 |
| ★★★ | 矫正视力 0.6 / 0.7 | 报告自相矛盾，需重新验光；不影响全身健康 |

每一项都能点开「凭什么 N 星」，看到上面的判断依据——不让星级变成黑箱。

### 3. 科室：不是每个都要去

体检报告能拆出 6 个科室方向，但**只有需要抽血、需要设备、需要处方的才值得跑一趟**。

| 科室 | 星 | 结论 | 理由 |
| :-- | :-- | :-- | :-- |
| 心血管内科 | ★★★★★★★ | 必须去 | Hcy 归因要抽血，补不补叶酸要处方 |
| 内分泌科 | ★★★★★★ | 必须去 | 甲功 + 抗体必须抽血；结节要专业评估 |
| 呼吸内科 | ★★★★★ | 必须去 | 肺功能复核需要设备 |
| 眼科 | ★★★ | 必须去 | 验光 20 分钟，但替代不了 |
| 消化内科 | ★★ | **可以不去** | 单纯性脂肪肝 + 肝功正常，一线处理就是减重；6 个月随体检复查超声即可 |
| 血液科 | ★ | **可以不去** | 白细胞总数正常、无贫血、血小板正常；先 1–3 个月复查血常规 |

并且给出**就诊分趟**：心血管内科 + 内分泌科都要空腹抽血 → 同一天上午一次抽完；呼吸内科 + 眼科都不用空腹 → 同一天下午。**两趟跑完 4 个科。**

这是这个产品最实用的一屏：它替你省掉一次挂号、一次排队、一次「医生说先回去减重」。

### 4. 不用秤的方案

「燕麦 40g + 鲈鱼 150g + 西兰花 200g」这种菜单没人能执行——家里没有厨房秤，也没人愿意每餐称。

改用**手掌量化法**（营养科常用估算法，误差约 20%）：

| 单位 | 大概是多少 | 对应 |
| :-- | :-- | :-- |
| 1 掌心 | 手掌心大小，厚度约等于小指 | 蛋白质约 100g 生重 |
| 1 拳头 | 自己拳头的体积 | 熟米饭/面条约 100g |
| 2 捧 | 双手并拢捧起 | 生叶菜 150–200g，炒熟一大盘 |
| 1 拇指 | 大拇指第一指节 | 油脂约 10g |
| 1 小把 | 单手抓一把 | 坚果约 15g |

每日目标：蛋白质 4–5 掌心 / 蔬菜 6 捧以上 / 主食 3 拳头 / 水果 1 拳头 / 坚果 1 小把 / 油 2.5 拇指 / 水 8 杯。

菜单本身**四周一轮、28 天不重样**（家常基础 / 换蛋白 / 加豆制品与海产 / 外食友好版），第 5 周回到第 1 套，随时可以「换一套」。

## 三、长期坚持：从一周到一年

只给一周计划是没用的——第二周就断了。

**运动按 12 个月排**，四档视图：

- **本周**：7 天逐日安排，可翻到第 1–12 个月任意一月，看当月模板（基础 / 强化 / 增肌 / 维持四种）
- **第 1 月**：四周怎么递进，每周只守三条
- **前 3 月**：减重主战场，每月的周有氧分钟、抗阻次数、里程碑
- **12 个月**：一张表，每月主题 + 里程碑 + 周量

**防掉队比训练表更重要**，所以单独写了一节：

| 断档情况 | 怎么接 |
| :-- | :-- |
| 断 1–2 天 | 直接接上，不用补练（双倍训练是受伤头号原因） |
| 断 3–7 天 | 从 60% 剂量重启一周 |
| 断超过 7 天 | 回到第 1 个月模板重来，别从断点接 |
| 实在没时间 | 做 10 分钟也算——10 分钟是 0 分钟的无限倍 |

加上：本周打卡（7 格，点一下算完成）、每 4 周复盘（称重 / 量腰围 / 看打卡率）、非食物奖励。

## 四、为什么把「吃」和「运动」拆成两页

### 试过、然后删掉的：形体预测

v2 里有一个「形体」页：用 Deurenberg 公式推体脂、指数衰减推体重曲线、参数化 SVG 人形跟着腰围变形，滑块拖到第 12 个月看「一年后的你」。

出发点没错——减重最难的是第 6–8 周，那时镜子里还没变化，把一年后的样子提前摆出来，是让人撑过这段路的办法。

**但它没做成。** 前后重画了 7 版：

| 方案 | 结果 |
| :-- | :-- |
| 几何近似（椭圆头 + 梯形颈 + 手写曲线躯干 + 拼装四肢） | 接缝明显、肩部鼓包、手臂和躯干贴成一坨 |
| 单条闭合轮廓（解剖关键点 + 单调三次插值） | 轮廓平滑了，但手臂必须画在躯干外才不会自交，肩宽被迫大于胸围，比例失真 |
| 叠解剖肌肉线（锁骨 / 腹直肌 / 腹外斜肌） | 变成线框示意图，比简单版更丑 |
| 硬描边勾轮廓光 | 多部件拼接的内部接缝全被描出来，像剖面图 |
| 手臂压暗一档（想做前后层次） | 读成「穿了深色外套」 |
| 最终版：多部件分层 + 模糊软阴影 + 手臂外展 6° + 头发 + 光晕 | 能看，但仍然像人体模型，不像人 |

**结论是：代码手绘写实人形，投入产出比不成立。** 一个不好看的人形图，会拖累整页的可信度——用户会想「这图画成这样，那结论准吗」。而它提供的激励价值，可以用更便宜的方式拿到（打卡率、体重周均值、腰围、训练重量）。

所以整块删掉了：`projectBody()`、`bodySVG()`、`bodyGeo()`、`partBody()` 全部移除，`view-body` 从页面里去掉。

### 换成了什么

把原来挤在一个「计划」页里的饮食和运动，拆成两个独立 Tab，各自写到能直接照做的程度。

原来三件事挤在一页，每件都只能写个大概。分开之后，每一页都有 9–12 个小节：

**怎么吃**

| 小节 | 解决什么问题 |
| :-- | :-- |
| 吃多少：用手量 | 六个手掌单位（掌心 / 拳头 / 捧 / 拇指 / 小把 / 杯）+ 七项每日目标 |
| 什么时候吃 | 起床到睡前的七段时间线，含每餐的比例 |
| 吃到几分饱停 | 五档饱腹感量表，第 3 档是目标 |
| 针对这份报告的四条 | 从报告异常项推出来的个性化要点，不是通用建议 |
| 四周轮换菜单 | 4 套 × 7 天，含一周外食友好版 |
| 买什么 | 按类别分的采购清单，含「需要清出厨房」一栏 |
| 周日 90 分钟备餐 | 五步，含「连 90 分钟都没有时只做哪三步」 |
| 饿了怎么办 | 按热量分四档的加餐清单 + 黑名单 |
| 怎么做 | 烹饪方式排序 + 控油 + 调味 + 绿叶菜别久煮 |
| 外食怎么点 | 食堂 / 外卖 / 火锅 / 烧烤 / 喝酒 |
| 五个最容易踩的坑 | 不吃主食、只吃水煮菜、果汁、忍着饿、周末放开吃 |

**怎么运动**

| 小节 | 解决什么问题 |
| :-- | :-- |
| 本周打卡 | localStorage，点一下算完成 |
| 一次训练分四段 | 热身 5 分 / 激活 5 分 / 主训练 30 分 / 放松 5 分 |
| 心率区间对照 | 低 / 中 / 高三档，按最大心率换算 |
| 五个动作，覆盖全身 | 深蹲、髋铰链、俯卧撑、划船、平板——每个都写了「常见错误」 |
| 没器械怎么办 | 零器械（一条弹力带）/ 一对可调哑铃 / 健身房，三档预算 |
| 有氧选哪个 | 快走 / 骑行 / 游泳 / 爬楼 / 跳绳，按关节负担排序 |
| 练多久、怎么递进 | 本周 / 第 1 月 / 前 3 月 / 12 个月四档，可翻到任意月份 |
| 记什么才算进步 | 体重（周）、腰围（月）、训练重量（次）、同角度照片（4 周） |
| 断了怎么接回来 | 断 1–2 天 / 3–7 天 / 超 7 天三档恢复规则 + 最低有效剂量 |
| 什么时候必须停 | 六条安全红线，胸痛 / 低血糖 / 关节刺痛 / 心率不降 / 发热 / 血糖过高 |

复查时间表挪到了「就医」页底部——它本质是医疗行为，不是生活方式。

### 打卡是怎么设计的

v4 第一版的打卡是「点一下就完成」，有几个说不通的地方，全部重做了：

| 问题 | 后果 | 现在的做法 |
| :-- | :-- | :-- |
| 不知道在打什么卡 | 点一下就算完成，但完成的是哪一次训练？ | 卡片直接显示「今天 · 周三 · 第 1 个月 · 有氧 / 骑行或游泳 40 分钟 / 目标心率 122–137」，主按钮是「完成这次训练」 |
| **未来的日子能点** | 用户可以把整周点满，进度直接 100% | `disabled` + 虚线框，点不动 |
| 进度按「已过天数」算 | 周一打一次就显示 100% | 按「周目标 4 次」算，和 KPI 口径一致 |
| 记录只有 0/1 | 回答不了「这周练了几次力量」 | 存 `{t:'strength'}`，格子里显示「抗 / 有 / 恢」 |
| 断档没有任何反馈 | 防掉队规则写了但用不上 | 距上次打卡 ≥3 天，主动提示「从原剂量的 60% 开始」 |
| 存储失败静默 | 无痕模式下点了没反应，用户以为坏了 | 显式提示「这个浏览器不允许本地保存」 |
| 换人后记录还在 | 分享给亲友时看到别人的数据 | 卡片底部有「清空记录」，带二次确认 |

数据结构：`{ '2026-11-04': { t: 'aerobic', at: 1730… } }`，存在 `localStorage` 的 `hl_checkin_v2`。旧版 `hl_checkin_v1` 的 `{日期: 1}` 会自动迁移，迁移后旧 key 删除。

交互规则：今天 → 主按钮或格子都能打；过去 → 格子可点，用来补记；未来 → 不可点。再点一次取消。

**为什么不做到「分钟数」**：让用户填「今天练了 38 分钟」会让打卡变成负担，第二周就没人填了。打卡只需要回答一个问题——今天动了没有。

### 这个改动背后的判断

原来那版的问题不是「内容不够多」，是**把两种完全不同的东西塞在一个页签里**：

- 饮食是「每天做三次的决定」，需要的是**具体的量和时点**
- 运动是「每周做三次的决定」，需要的是**动作标准和长期递进**

混在一起，两边都只能写个提纲。分开之后，每一页都能写到「照着做就行」的颗粒度。这也是这次唯一真正增加价值的地方——不是加了功能，是加了可执行性。

### 为什么需要模板层

v2 的文案是写死的：

```js
depts.cardio.why = '同型半胱氨酸 19.5 μmol/L 超出上限 30%…'
```

换一个人上传报告，屏幕上还是显示 19.5。这不是排版问题，是**这份产品只能服务一个人**。

v3 把文案改成模板：

```js
depts.cardio.why = '同型半胱氨酸 {hcy.v} {hcy.u}，超出参考上限 {hcy.over}%…'
```

`HL.tpl.render()` 在分析时把占位符替换成这份报告的真实值。取不到值输出「—」，永不抛错。

**模板语法**

| 写法 | 含义 | 例 |
| :-- | :-- | :-- |
| `{hcy.v}` | 数值 | 19.5 |
| `{hcy.u}` | 单位 | μmol/L |
| `{hcy.hi}` / `{hcy.lo}` | 参考上下限 | 15 / 0 |
| `{hcy.over}` | 超出上限的百分比 | 36 |
| `{hcy.s}` | 状态词 | 偏高 / 偏低 / 正常 |
| `{?hcy}…{/hcy}` | 该项存在才输出 | — |
| `{^hcy}…{/hcy}` | 该项缺失才输出 | — |
| `{_sex}` | 引擎算好的派生值 | 男 / 女 |

### 判断也必须是动态的

只改文案不够。v2 的星级和严重度是写死的常量，导致「空腹血糖 7.2」和「空腹血糖 5.2」拿到同样的分数——换人之后，一份糖尿病报告反而比一份轻度异常报告分数更高。

v3 把两者都改成数值驱动：

```js
// 星级：可以是数字，也可以是吃上下文的函数
fbg: {
  s: function (c) {
    if (!c.fbg) return 0;
    if (c.fbg.v >= 7.0) return 7;   // 糖尿病诊断线
    if (c.fbg.v >= 6.1) return 5;   // 糖尿病前期
    if (c.fbg.v >= 5.6) return 2;
    return 0;
  }
}

// 严重度由星级推导，不再单独写死
r.severity = sv >= 7 ? 3 : sv >= 5 ? 2 : sv >= 3 ? 1 : 0;
```

科室分流也会跟着翻：

- 脂肪肝 + 肝功正常 → 消化内科判 `skip`（减重就能解决，不用挂号）
- 脂肪肝 + 转氨酶升高 → **自动翻成 `must`**，星级升到 5，期限改为 1 个月内

### 200 项指标，怎么写文案才写得完

一份体检报告动辄 60–120 项，各家医院的项目名还不一样。如果每项都手写一段解读，扩到 200 项就是 200 段文案——写不完，也维护不了。

所以拆成两层：

**第一层：字典（`js/dict.js`）——只管「这项是什么」**

```js
D('hcy', '血同型半胱氨酸', 'μmol/L', [0, 15], 'high', 'hcy', { rule: 'hcy' });
D('uric', '尿酸 UA', 'μmol/L', [208, 428], 'high', 'renal',
  { rule: 'uric', sexRef: { 男: [208, 428], 女: [155, 357] } });
D('hdl', '高密度脂蛋白', 'mmol/L', [1.04, 1.42], 'both', 'lipid',
  { benignMax: 2.5 });
```

200 项全部按这个格式登记：名称、单位、参考区间、方向（偏高才有意义 / 偏低才有意义 / 双向）、所属家族。性别差异用 `sexRef`，良性项的上限用 `benignMax`。

**第二层：家族（`HL.fam`，41 个）——只管「这一族怎么理解」**

「肝酶与胆红素」这一族只需要写一次：为什么升高、为什么降低、怎么办、多久复查。凡是归到这一族、又没有专属文案的项，自动套用这段话。

**结果：新增一项指标 = 加一行 `D(...)`。** 不需要改引擎、不需要写文案、不需要改视图。

### 三条兜底路径，保证异常项不会消失

| 情况 | 去哪 | 显示成什么 |
| :-- | :-- | :-- |
| 有专属文案（17 项） | 独立的关注项卡片 | 完整解读 + 怎么做 + 复查 + 科室 |
| 同族已有专属卡 | 合并进那张卡 | 「同族其他项：AST 70 / GGT 130」 |
| 有家族但无专属卡 | 家族聚合卡 | 按偏离幅度定星：10–25% → 2★，25–50% → 3★，>50% → 4★ |
| 偏离不到 10% | 「轻度偏离」折叠区 | 一行摘要，点开看每项 |
| 影像描述 | 影像卡 | 按 `ruleId` 或家族模板给建议 |

实测覆盖：全异常（所有数值 ×1.9、所有影像异常）能出 25 张关注项卡，没有一项被静默丢弃；全正常报告只剩 1 张「甲功未查」的缺项卡。

### 良性项也有上限

HDL 偏高是好事，但高到 2.8 mmol/L 就不是了。字典里给 HDL 写了 `benignMax: 2.5`，超过这个值它就从「假警报」桶里出来，变回需要关注的项。

这条规则是被测试逼出来的：全异常压力测试里 HDL 被拉到 2.8，卡片仍然写着「其实不用管」——那显然是错的。

### 拍照识别：为什么不用云 OCR

先说结论：**这件事不需要 API，也不需要后端。** 一张体检报告照片从进来到变成结构化指标，全程在浏览器里跑完，图片一个字节都不离开设备。

这不是为了炫技，是因为医疗数据的信任成本太高。「你的体检报告上传到我们的服务器」这句话，劝退的人比吸引的多。

#### 四步预处理，缺一不可

Tesseract 直接吃体检报告会彻底失败——表格线被当成笔画，行切分全乱，18 项能认出来的不到 2 项。同一张图加上预处理后，置信度从 50 跳到 87，18 项全中。

| 步骤 | 做什么 | 不做会怎样 |
| :-- | :-- | :-- |
| 灰度 + Otsu | 自动找二值化阈值 | 固定阈值在暗光照片上必然翻车 |
| 去长线 | 连续黑像素超过单元格宽/高就算表格线，擦掉 | 表格线把行切断，一列文字被拆成几十个碎片 |
| 纠偏 | 用**去线后的纯文字**算投影角，转正 | 手机拍纸一定歪，线一歪 run-length 去线就失效，整条链路崩掉 |
| 再来一遍 | 转正后重新二值化 + 去线 | 旋转引入的插值灰边会让线重新粘连 |

纠偏必须用「去过线的纯文字」来测角度：表格线是超强信号，会把文字的行投影完全盖住，测出来永远是 0°。

#### 为什么结果必须让人核对

这份代码实际认错过这些字：

| 原字 | 认成 | 后果 |
| :-- | :-- | :-- |
| 谷丙转氨酶 | 谷丙转**氮**酶 | 靠编辑距离救回 |
| 高密度脂蛋白 | 高密度脂**蛇**白 | 靠编辑距离救回 |
| 肌酐 | 肌**酝** | 名字废了，靠缩写 `Cr` 救回 |
| 尿蛋白 2+ | 尿蛋白 **2** | `parseFloat('2+')` 得 2，定性值变数字，判成正常 |

最后一条最危险：它不会报错，不会显示为空，就是**静默地把一项异常判成正常**。所以设计上做了两件事：

1. **识别完先进核对页**，不直接出结论。核对页列出「标准名 + 原文 + 数值」，原文和标准名不一致时把原文并排显示，让人一眼看出哪里认错了。
2. **定性值不转数字**：只有整串都是数字才 `parseFloat`，`2+`、`±`、`阴性` 保持字符串。

核对页还有一条兜底：名称对不上指标库时，那行**照样列出来**并标红，给一个下拉让用户指定，或者删掉。静默丢弃会让用户以为报告里没这项。

#### 缩写列是第二道保险

「肌酝 Cr 78」里名字彻底废了，但 `Cr` 是准的。所以解析时顺带取缩写列（全字母且不含 `/`，含斜杠的是单位），名称匹配失败就拿缩写再试一次。这一条把「γ-谷氨酰转肽酶」和「肌酐」都救回来了。

#### 实测

| 输入 | 尺寸 | 识别 | 匹配 | 耗时 |
| :-- | :-- | :-- | :-- | :-- |
| 清晰截图 | 1520×1800 | 18 项 | 18/18 | 3.4s |
| 拍照（倾斜 0.9° + 模糊 + JPEG） | 2280×2700 | 18 项 | 18/18 | 3.9s |
| 手机原图 | 4070×4770 | 18 项 | 18/18 | 2.5s |

体积代价：引擎 + 中文语言包 5.7MB，**首次点「识别」才下载**，之后走 SW 缓存优先，第二次识别不再下载。语言包用的是 `chi_sim` 的 fast 版（1.7MB）——实测它在拍照图上反而比 20MB 的 best 版更准（15 项 vs 13 项），而且快一倍。

缩放上限 2400px 是调出来的：1800 会把手机拍的字压糊，同一张图从 15 项掉到 5 项。

### 分享卡：为什么不引 html2canvas

需求很朴素：把结论发给家人。截图截出来一半是折叠卡、一半是免责声明，发出去没人看。

为了导一张图引 200KB 的库不划算，所以 `js/share.js` 用 canvas 手画，代价是所有排版自己算。

三个必须记住的坑：

1. **测量和绘制必须用同一套字体。** 一开始忘了给测量用的 ctx 设 `font`，`measureText` 全按 10px 算，所有文字都「很短」，永远不换行——缺失项列表直接冲出画布右边。这个 bug 只有看图才能发现，日志里什么都没有。
2. **字距只给中文加。** 手写 letterSpacing 逐字加间距，「HealthLens」会被拉成「H e a l t h L e n s」。改成只对 CJK 字符生效。
3. **高度先排一遍再画。** 用同一套 ops 队列先算 y 游标得到总高，再建真 canvas 回放，避免固定高度留白或截断。

内容取舍：卡片上**不出现姓名、不出现报告原文**，只有分数、三件要做的事、缺了哪几项。这是让人敢往群里发的前提。

低完整度（< 60%）时额外加一行琥珀色提示「查得太少，这个分数参考价值有限」——只查两项也能拿 100 分，这张图要是发出去，等于在骗人。

### 和上次比：方向不能看数值涨跌

没有 OCR 就拿不到第二份报告，所以趋势做的是**手动补录**：用户手边一定有上一次的纸质报告，抄几个关键数字即可，不需要后端。

判断好坏用的是「离参考区间多远」，不是数值涨跌：

- 尿酸 390 → 400.0，涨了，但两次都在 208–428 内 → 「两次都在区间内」
- HDL 1.05 → 1.50，也涨了，从偏低变成正常 → 「已回到区间内」
- 空腹血糖 5.0 → 5.4，涨了 8%，但都没超 6.1 → 不算变差

两个必须处理的例外，否则会把好转说成恶化：

| 例外 | 例子 | 处理 |
| :-- | :-- | :-- |
| `dir === 'low'`：只有偏低算异常 | 血氧 100、视力 2.0、eGFR 200 都在区间外，但没人认为这是病 | 高于上界一律视为 0 偏离 |
| `benignMax`：高到某值以内算良性 | HDL 1.50 超上限 1.42，但这是好事 | 未超 `benignMax` 视为 0 偏离 |

不做这两个例外，HDL 从 1.05 升到 1.50 会被判成「和上次差不多」——而它其实是这份报告里最值得高兴的一项。

候选行排序也踩过坑：一开始按报告里的原始顺序取前 14 项，排头的是 RDW-CV、淋巴细胞百分比这类边缘项，把尿酸和血糖挤到列表外——用户抄了半天，最该比的两项没抄到。改成**异常项按偏离幅度降序取 8 项，再用 14 个核心项补满**。

### 分层职责

**tpl.js — 模板层**
- `render(str, ctx)`：替换占位符 + 处理条件块（支持嵌套）
- `deep(obj, ctx)`：把对象里所有字符串（含数组）过一遍
- 这一层刻意做得很薄：不带任何业务判断，只做替换

**data.js — 知识层**
- `HL.rules`：每条规则 = 名称 / 健康域 / 一句话结论 / 详细解读 / 行动清单 / 关联科室 / 复查周期 / 数据等级。文案里只写模板，不写具体数值
- `HL.starMeta`：星级函数 + 「凭什么 N 星」的判断依据
- `HL.depts`：科室 = 为什么去 / 星级 / `need: must|skip` / 建议时间 / 就诊前准备 / 问诊三问 / skip 理由与「什么情况再去」
- `HL.sample` / `HL.sample2`：两份异常谱完全不同的示例报告，用于验证「换人」
- `HL.plan`：手掌量化 / 一天时间线 / 饱腹感量表 / 4 套菜单 / 采购 / 备餐 / 加餐 / 烹饪 / 五个误区 / 12 个月方案 / 4 套周模板 / 训练四段 / 五个动作 / 器械 / 有氧 / 安全红线 / 记录 / 防掉队

**engine.js — 计算层**
- `buildCtx(report)`：把报告整理成可查的表（指标值 / 单位 / 参考区间 / 偏离百分比 / 派生词）
- `applyStars(ctx)`：按上下文算每条规则的星级与严重度
- 判定：`ref` 区间比对；单边区间（`< 3.4`）支持
- 扣分：严重度 3→25 / 2→15 / 1→7 / 0→0；同域多项递减 50%
- 综合分：8 域加权平均（心血管 0.20、代谢 0.16、肝/内分泌各 0.12、其余 0.10）
- 科室分流：`need === 'skip'` 进 `skipDepts`，其余进 `depts`；空腹项按 `TRIP` 表分趟；科室星级 = `min(科室固有优先级, 触发它的规则星级)`
- 缺项识别：做了甲状腺超声却无甲功 → 记「缺项」，不扣分但单独提示
- 计划推算：Mifflin-St Jeor 算 BMR → ×1.4 → 减 500 kcal → 反推三大营养素

**app.js — 视图层**
- 5 个 section（上传 / 总览 / 就医 / 怎么吃 / 怎么运动）+ 底部 4 Tab
- 视图层**不碰模板**：引擎交出来的已经是渲染好的字符串，app.js 直接显示
- 假警报、「凭什么 N 星」、完整解读都是就地展开，不重渲染（避免滚动跳动）
- 饮食页与运动页各自独立渲染，互不影响：`renderDiet(r)` / `renderTrain(r)`

**share.js — 分享卡**
- `build(r)` → canvas，`open(r)` → 弹层（长按保存 / 下载按钮），`dataURL(r)` 供自动化测试
- 零依赖手绘；高度先排一遍再画，`toDataURL` 出 1500×2600 的 PNG

**trend.js — 历史对比**
- `load/push/clear`：`hl_hist_v1` 存最多 12 条 `{at, vals}`，同一月份只留最新
- `judge(cur, prev, ref, meta)`：按偏离幅度判断「变好 / 变差 / 没变」，处理 `dir:'low'` 与 `benignMax` 两个例外
- `mount(root, r, onChange)`：渲染空状态 / 对比表 / 补录表单，三态互斥

**ocr.js — 拍照识别**
- `recognize(file, onStep)` → `{items, hit, total, angle, conf}`：引擎懒加载 → 预处理 → 识别 → 行级解析 → 字典匹配
- `mountVerify(host, res, onConfirm, onCancel)`：核对页，含年龄性别、逐行数值编辑、未识别行下拉指定、删行
- 依赖 `vendor/ocr/` 四个文件（5.7MB），首次识别才下载；不预缓存进 SW，走运行时缓存优先

**pdf.js — PDF 解析**
- `parse(file, onStep)`：文字层优先 → 按 y 坐标聚行 → 复用 `HL.ocr._parseLines` → 进同一套核对页
- 扫描件兜底：全页文字总数 < 50 判定为图片型 PDF，用 `page.render()` 转 canvas 后交给 OCR
- `pickProfile(lines)`：从抬头抓年龄/性别（只认 `年龄：45` / `性别：男` 这种明确标注，抓不到就留空，**绝不猜**）
- 依赖 `vendor/pdf/`（1.4MB），只有选了 PDF 才注入 `<script>`，首屏零请求

**summary.js — 就诊摘要**
- `open(r, who)`：弹层预览，`body.sum-open` 作用域限定，只在摘要打开时才隐藏其他内容
- 五项内容：抬头 / 问医生三句话（按科室分组取 `dept.ask`）/ 异常项清单（含上次对比）/ 吃动各 3–4 条 / 免责声明
- 打印：`@media print` 下 `body.sum-open > *:not(#sumSheet)` 整体隐藏，只留摘要
- 存图：独立竖版 canvas（750px 宽），高度先按 4000 画再裁掉空白——**不能按行数估算高度**，少算一行免责声明就被裁掉
- `ageText(p)`：报告没写年龄栏时引擎按 30 岁兜底（`engine.js` 的 `p.age || 30`），所以摘要要显示「按 30 岁估算」而不是「—」，否则和按 30 岁算出来的分数自相矛盾

### 换人测试

上传页有两个入口：

1. **样板报告 A**（构造示例数据）：Hcy 高 + 脂肪肝但肝功正常 + 视力不达标 → 86 分，心内 / 呼吸 / 眼科为主
2. **示例报告 B**（构造数据）：血糖 7.2 + 肝功异常 + 血压 145/92 → 84 分，内分泌 / 消化 / 心内为主，代谢域只有 59 分

同一套代码、同一个引擎，两份报告给出完全不同的科室清单和优先级。这是判断「能不能给别人用」最直接的方法。

### 还没解决的

1. **影像文本的结构化目前是可选的**。`imaging[].finding` 本身仍是自由文本（"左叶低回声结节 6×4mm，TI-RADS 3 类"），模板层读不到里面的数值。AI 影像结构化（见第十之二节）会把异常影像描述抽成部位、尺寸、边界、钙化等字段补进卡片，但只在自配本机代理时启用，公开版保持原文。所以甲状腺、脂肪肝、肺功能这几条的文案仍写成不依赖具体形态的通用表述。要让规则引擎直接吃这些字段、并覆盖全部影像项，还有一步没做。
2. **评分会被「查得少」拉高**。报告里没做的项目，域分数默认 100。结果是一份只查了 20 项的报告可能比查了 70 项的分数还高。
   - 已做：总览页与分享卡都显示「11 个常见项目里查了几项」，并写明「没查到的项目不参与评分，所以这个分数可能偏高」
   - 未做：只在有数据的域之间重新加权。这个改动会改变所有已有报告的分数，需要先定一套新基线，暂时没动
3. **肿瘤标志物异常不推科室**。这是刻意的：体检发现的肿瘤标志物轻度升高绝大多数是假阳性，直接推肿瘤科会制造恐慌。现在的处理是「4–6 周复查同一项，持续升高再看专科」，写在这一族的文案里。

### 评分模型的可信边界

综合分只反映**检验指标的偏离程度**，不含症状、病史、家族史、影像的完整判读。它适合做趋势跟踪，不适合做健康结论。UI 上用「指标正常率」和「需跟进项数」并列呈现，避免单一数字误导。

## 六、接入真实 OCR 的三条路

当前识别层是空的。要变成真产品，必须解决「图片 → 结构化指标」。

| 方案 | 准确率（中文体检单） | 成本 | 落地难度 | 适合 |
| :-- | :-- | :-- | :-- | :-- |
| 通用 OCR（腾讯云/百度/阿里 OCR） | 中 | 低（几分钱/次） | 低 | 快速验证 |
| 通用 OCR + 大模型抽取 | 较高 | 中 | 中 | **推荐** |
| 医疗专用 OCR（厂商医疗版） | 高 | 高 | 中 | 规模化后 |

**推荐路径：通用 OCR 拿文本 → 大模型做结构化抽取 → 规则引擎做判定。**

理由：体检单版式千差万别（各医院模板不同），纯模板匹配必然崩。但「项目名 / 结果 / 单位 / 参考值」这四列的语义是稳定的，大模型抽取的鲁棒性远高于正则。判定环节仍交给确定性规则引擎——**不让模型直接下医学结论**，这是可解释性和安全性的双重要求。

抽取层输出统一 schema：

```json
{
  "profile": { "sex": "男", "age": 40, "height": 175, "weight": 82 },
  "items": [
    { "id": "hcy", "name": "血同型半胱氨酸", "value": 19.5,
      "unit": "μmol/L", "ref": [0, 15], "panel": "同型半胱氨酸" }
  ],
  "imaging": [
    { "id": "thyroid", "panel": "甲状腺超声",
      "finding": "左叶低回声结节 6×4mm…TI-RADS 3 类",
      "ruleId": "thyroid" }
  ]
}
```

只要产出这个 schema，`HL.engine.analyze()` 原样复用——引擎与识别层完全解耦，换 OCR 供应商不影响下游。

## 七、能不能做成小程序 / APP

**结论：以个人主体做微信小程序，这条路基本走不通。** 这是硬门槛，不是技术问题。

查证结果（2026-11 核实）：

1. **类目限制**：微信「医疗健康」相关类目需要《医疗机构执业许可证》或《诊所备案凭证》，且诊疗科目要与服务内容匹配。个人主体无法选择该类目。
2. **个人主体可做的类目**：仅限纯展示、工具、资讯类。本产品核心是「指标解读 + 就医建议」，实质落在医疗健康范畴。
3. **备案是前置条件**：小程序上线前必须完成 ICP 备案（平台初审 1–2 工作日 + 管局 1–20 工作日）。
4. **APP 同理**：国内应用商店对医疗健康类 App 要求相应资质。

### 三条可行路线

| 路线 | 主体要求 | 优点 | 代价 |
| :-- | :-- | :-- | :-- |
| **A. H5 网页（当前形态）** | 无 | 零审核、最快验证、可微信内打开 | 无推送、留存弱、需自行引流 |
| **B. 小程序（企业主体 + 资质）** | 企业 + 医疗资质，或与体检机构合作挂靠 | 体验最好、传播链路顺 | 资质门槛高、周期长 |
| **C. 小程序（工具类目，降级定位）** | 个人可试 | 门槛低 | 必须删掉「解读/建议」，只剩「记录/趋势」——产品价值大幅缩水 |

**当前选择 A**：不上架也要做成成熟产品——分享给亲友、挂到网站做引流、发到 GitHub 与开发者社区。

### 但它已经能「装」到手机上

虽然是网页，现在具备 PWA 能力，在手机上和 APP 的差别只剩「没有应用商店图标」：

| 能力 | 实现 |
| :-- | :-- |
| 加到主屏幕 | `manifest.json`（standalone、竖屏、主题色 `#0A6E75`、3 个图标含 maskable）；上传页有一张「装到手机主屏」卡，安卓 Chrome 命中 `beforeinstallprompt` 时右侧直接出现**「一键安装」**按钮 |
| 全屏无地址栏 | `display: standalone` + `apple-mobile-web-app-capable` |
| 断网可用 | Service Worker 预缓存 18 个资源；**network-first**，改了代码能立刻生效。识别引擎 5.7MB 不预缓存，首次用过之后走缓存优先 |
| 记住上次状态 | 刷新后自动回到上次的报告，不用重新点一遍 |
| 刘海屏适配 | `viewport-fit=cover` + `env(safe-area-inset-bottom)` |

iOS 上用 Safari 打开 → 分享 → 「添加到主屏幕」；Android 用 Chrome 打开会直接弹「安装应用」。**已经是 App 模式（`display-mode: standalone`）时，安装卡会自动隐藏**，不再劝装第二次。

注意：PWA 只在 `https://` 或 `localhost` 下注册 Service Worker，`file://` 直接双击打开时不会启用（浏览器限制），但页面本身照常能用。

### 电脑上不是细长条，是双栏网页

同一份代码，两种形态，**断点只有一个：900px**。

| | 手机（<900px） | 电脑（≥900px） |
| :-- | :-- | :-- |
| 主体宽度 | 100% | `.app` 加宽到 **860px**（两侧留白 210px） |
| 健康维度条 | 单列 | `.domain-grid` 两列，各约 382px |
| 关注项卡片 | 单列 | `.findings-grid` 两列；**第一张「优先处理」卡跨两栏**（`grid-column: 1 / -1`） |

为什么是 860：两栏各约 382px，**正好等于原来的手机设计宽度**——排版、字号、卡片内边距都不用改，内容不会因为拉宽而变形。加宽到 1100 以上会让每行文字过长、读起来累，所以到此为止。

**分享给别人就一个链接**：`https://jmsjbeb.github.io/healthlens/`。微信里点开会用内置浏览器打开（能正常用，但装不成 App）；想让对方装到桌面，让他点右上角「在浏览器打开」再装。

### 提醒：能不能推到微信 / 飞书 / 手机号

用户真正的问题是「到饭点、到训练时间能不能叫我一声」。五条通道逐条查过（2026-11 核实）：

| 通道 | 能长期自动推吗 | 卡在哪 | 现在能做吗 |
| :-- | :-- | :-- | :-- |
| 小程序订阅消息 | **不能** | 一次性订阅每授权一次只发一条；长期订阅只对政务/医疗/交通/金融/教育等**线下公共服务类目**开放，医疗下仅「挂号预约 / 报告查询 / 疫苗接种 / 处方配送 / 医保进度」等二级类目，体检中心不在其中；个人主体连医疗健康类目都选不了 | 否 |
| 公众号 / 服务号 | **不能** | 模板消息已改为「订阅通知」，同样一次性；服务号需企业主体认证 | 否 |
| 短信（手机号） | 能 | 需企业资质 + 签名报备 + 模板审核，按条计费；个人几乎拿不到签名 | 否 |
| 飞书机器人 | 能 | 需要企业/团队 + 自建应用，且要求用户装飞书——体检人群不会为此装一个办公软件 | 否 |
| **手机日历（.ics）** | **能** | 无需任何资质与服务器；导入后由系统日历负责提醒，跨平台、可随时改时间或删除 | **已实现** |
| 本地通知（打包成 APP） | 能 | 需 Capacitor / uni-app 打包 + 应用商店资质 | 后续 |

**已经落地的方案**：训练页与饮食页各有一个「加进日历」按钮，生成标准 `.ics` 文件——训练 7 条（每天一条、每周重复、共 12 周，19:00，提前 10 分钟提醒），三餐 3 条（7:30 / 12:00 / 18:30，每日重复，共 12 周）。导入后时间是活的：想改成早上练，在日历里改一次，所有重复项一起变。

设计取舍：**日历只负责「叫你」，不负责「告诉你练什么」**。内容随月份变化（基础期 → 增量期 → 力量期 → 维持期），写死进日历会过期；所以事件标题只写类型，正文写「以康鉴当周安排为准」，点开 app 才看当天内容。

### 内容合规红线（无论哪条路线）

- 不出现「诊断」「确诊」「治疗方案」「用药建议」等表述
- 不给具体药物剂量（「叶酸 0.4–0.8mg/日」已注明「需由医生决定」）
- 每屏保留免责声明
- 不做疾病风险预测百分比（如「你 5 年内患癌概率 X%」）
- 报告数据默认本地处理，明示不上传

## 十、这一轮修掉的坑（逻辑 / 联动 / 数据）

把四个页签的每个按钮都点了一遍，再拿五份极端报告跑压力测试，找出并修掉的问题：

### 逻辑

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 评级话术写死 | 66 分、23 项待跟进的报告，标题还写「整体可控」 | 评级跟分数走：≥90 状态不错 / ≥80 整体可控 / ≥70 有几件事要处理 / 其余需要认真对待 |
| 扣分归因写死 | 永远写「问题集中在心血管代谢与内分泌两条线」，换份报告就错 | 从八个维度里取分数最低的 1–2 个，动态生成 |
| 空报告算 100 分 | 扫描件 PDF 一项都没解析出来，页面显示「状态不错」 | 引擎标 `isEmpty`，视图换成「这份报告里没读到检查结果」+ 两个出口 |
| 空报告正常率 NaN | 分母为 0，页面出现 `NaN%` | 分母为 0 时给 0 |
| 报告对象不完整直接崩 | 少一个 `profile` 字段就白屏，`analyze()` 抛异常 | 入口兜底：`report \|\| {}`、`items \|\| []` |
| 科室星级被固有值压低 | 出现「7 星的病去 5 星的科」 | must 科室的星级不低于触发它的规则星级 |
| 运动页写死别人的数值 | 「你尿酸 400.0 已接近上限」——换份报告还是这句 | 从当前报告取 `uric`，按超限 / 接近 / 正常三种情况分文案 |
| 良性项无上限 | HDL 拉到 2.8 仍写「不用管」 | 字典加 `benignMax: 2.5`，超限自动翻成需要关注 |

### 按钮联动

原来四个页签彼此独立：总览里看到「科室 · 心内科」，想看得自己切到就医页再从六个科里翻。

现在：

- **关注项卡片里的科室 chip 可点** → 直接跳到就医页对应的科室卡，并闪一下高亮
- **就医页底部** → 「除了去医院，还能自己做什么」（饮食）/「运动怎么配合」（运动）

全部走同一套 `data-jump` 委托，新增跳转只需要加一个属性。

### 第 6 轮：扩字典、补趋势、出分享卡

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 参考区间只认数组 | 数据源给 `"7-40"` 时 `ref[1]` 是 `'-'`，比较得 NaN，谷丙 60 被判正常 | 加 `normRef()`：数组 / `{lo,hi}` / `"7-40"` / `"<40"` / `">7"` 全归一化 |
| 值不是数字时又静默正常 | 值是「阴性」而参考区间存在，`'阴性' > 40` 永远 false | 非数值走 `qualStatus` |
| 定性项整类漏判 | 尿蛋白 2+ 没有参考区间，被判 normal，卡片上直接消失 | `qualStatus` / `qualStars`，± → 2★，1+ → 3★，2+ → 4★ |
| 负数下界算出 −80% 偏离 | 骨密度 T 值 −1.8 被塞进「轻度偏离」折叠区 | `devOf` 加 `lo > 0` 守卫 |
| 8 个家族没有科室 | 尿蛋白、前列腺、妇科、骨密度异常，一条就医指引都没有 | 科室从 6 个扩到 11 个，家族补 `dept` |
| 模糊匹配只有 45% | OCR 出来的名字对不上字典，异常项静默消失 | 别名表 + 去英文后缀归一化 + 纯英文分支，60/60 命中 |
| 误配「前白蛋白」→ 白蛋白 | 白蛋白正常、前白蛋白偏低时，会把正常项当成异常 | 加 `EXCLUDE` 黑名单，优先级：宁可匹配不上，也不能误配 |
| 分享卡测量字体不一致 | 缺失项列表冲出画布右边，日志里没有任何提示 | 测量前设 `ctx.font`，与绘制用同一套 |
| 趋势把好转说成没变 | HDL 1.05 → 1.50 判成「和上次差不多」 | 处理 `dir:'low'` 与 `benignMax` 两个例外 |
| 补录列表把重点项挤掉 | 前 14 项全是 RDW-CV、淋巴细胞百分比，尿酸血糖不在里面 | 异常项按偏离幅度降序取 8 项，再用核心项补满 |

### 第 7 轮：接上拍照识别

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 表格线毁掉行切分 | 18 项只认出 2 项，置信度 50 | 去长横线/长竖线，同一张图置信度 87、18 项全中 |
| 倾斜让去线失效 | 拍照版（歪 0.9°）中文名大面积认错 | 用去线后的纯文字测投影角，转正后重跑一遍 |
| 缩太狠字会糊 | 上限 1800px 时拍照版从 15 项掉到 5 项 | 上限放到 2400px，配 findSkew 采样步长 4 抵消开销 |
| `parseFloat('2+')` 得 2 | 尿蛋白 2+ 被当成数字 2，判成**正常**，最该报的一项静默消失 | 只有整串是数字才转数值 |
| 行首非中文被整行跳过 | 「γ-谷氨酰转肽酶」消失，结果页少一项 | 允许行首是希腊字母或单个拉丁字母（OCR 常把 γ 认成 Y） |
| 名称认错就整项丢失 | 「肌酝 Cr 78」名字废了 | 顺带取缩写列，名称失败用缩写兜底 |
| 编辑距离救不回错字 | 「谷丙转氮酶」匹配不上，因为候选池只有字典名 | 候选池并入别名表；短名要求候选唯一防误配 |
| 噪声行被当成指标 | 核对页出现「攻了 3」「检验前 1」 | 页眉页脚/表头/结论词表过滤，`体重(?!指数)` 避免误伤体重指数 |
| 演示模式横幅过时 | 识别完了还写「尚未做 OCR 识别」 | 换成「来自你上传的报告 + 识别出 N 项」 |
| 核对页名称被截断 | 320 宽下「高密度脂蛋白胆固…」看不出是哪项 | 名称允许折两行 |

### 第 8 轮：全量审计 + PDF / 多档案 / 就诊摘要

这一轮先做了一次不预设结论的审计（引擎边界 22 组、四页交互、脏 localStorage 8 种、窄屏 5 档），挖出来的问题比预期严重得多。

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| **参考区间从不兜底字典** | `ALT 200`（参考 7–40）→ **100 分 0 异常项**；`ALT 999999` 同样 100 分。报告没印区间、OCR 没抽到区间、外部只给 `{id,value}`，全部判正常 | `normRef(it.ref)` 为 null 时回退 `HL.dictById[id].ref`，`sexRef` 优先 |
| **`sexRef` 从未被使用** | 血红蛋白、红细胞、腰围、腰臀比、体脂率一直按同一标准判，男女不分 | 兜底时按 `profile.sex` 取 `sexRef[男/女]` |
| 单位不换算 | 修好兜底后，`HGB 15.4 g/dL`（=154 g/L 正常）被**主动**判成严重偏低 | 6 类英制单位换算表 + `it._unitConv` 留痕，核对页显示换算过程 |
| 引擎不补 name/unit | `{id:'hgb',value:120}` 直接崩在 `famWhy` 的 `it.name.split('（')` | id 归一化后补字段（不覆盖 OCR 原文名）+ `famWhy` 防御 |
| items/imaging 非数组崩 | `{items:'abc'}` 抛 `items.forEach is not a function`（字符串也有 `.slice()`） | `Array.isArray()` 守卫 |
| 5 条规则漏配科室 | 尿酸、前列腺钙化、甘油三酯、LDL、ALT 没有 `dept`，就医页不给科室去向 | 补 `dept` + `recheck`（hdl/rdw/bmi 无 dept 是正确的，良性项不用跑医院） |
| **引擎缺失时用样板冒充用户报告** | `HL.ocr` 不存在时点识别 → 渲染 `HL.sample` 的 86 分，落盘标记 `kind:'upload'`，文件名是**用户的** | 明确报错并停在上传页；绝不出分数、绝不落盘 |
| 配额满静默丢数据 | `saveReport` 的 `catch` 是空的，用户以为存好了，刷新发现没了 | 统一 `warnStore()`，去重只弹一次；正常路径 0 弹窗 |
| 样板动画 3.3 秒 | 本地写死的数据也要「扫描」3.3 秒，中年人直接劝退 | 样板路径步长 300ms→60ms，实测 3332ms→888ms |
| 上传区键盘不可达 | `.dropzone` 是 `div`，Tab 到不了，屏幕阅读器不认 | `role="button" tabindex="0"` + Enter/Space + `:focus-visible` 轮廓 |
| 打卡日期不补零 | `2026-11-3` 与 `2026-11-10` 按字符串排序时前者更大，跨月跨年历史会乱序 | 补零 + 幂等迁移（旧 key 补零写回，垃圾 key 跳过不抛错） |
| 摘要年龄显示「—」 | 引擎实际按 `p.age || 30` 算的分和计划，摘要却写「不知道你多大」 | `ageText(p)` 统一函数：有 ageNote 就显示「按 30 岁估算」 |

**PDF 解析的两个坑**

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 文字层是碎词 | 直接读 `textContent` 得到一堆单词，不是整行 | 按 `transform[5]`（y）聚行，组内按 `transform[4]`（x）排序 |
| 扫描件没有文字层 | 医院导出的大多是图片型 PDF，抽出来是空的 | 全页字数 < 50 判定为扫描件，`page.render()` 转 canvas 交给 OCR |

**多档案的两个坑**

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 「重新上传」静默销毁数据 | 一个按钮干两件事：换报告 + 删档案，点错一次就没了 | 改成只换报告，档案保留；真正的删除走成员清单（有 confirm） |
| 打卡数据串成员 | 一家人共用一台手机，打卡混在一起没有意义 | key 加成员后缀 `hl_checkin_v2::<id>`；删成员时连带删该成员的打卡 |

**就诊摘要的两个坑**

| 问题 | 现象 | 修法 |
| :-- | :-- | :-- |
| 打印带上导航栏 | `@media print` 全局生效会波及别处 | 用 `body.sum-open > *:not(#sumSheet)` 作用域限定，只在摘要打开时隐藏其他内容 |
| canvas 高度算不准 | 按行数估算高度，少算一行免责声明就被裁掉 | 先按 4000px 画完，再测量实际内容高度裁掉空白 |

## 十之二、AI 影像结构化（可选增强）

把超声/CT 的自由文本（「甲状腺右叶结节 6×4mm，边界清，无钙化」）抽成结构化的 `{organ, location, type, size_mm, margin, calcification, impression}`，补进影像卡。**模型只做抽取归一化，星级/科室判定仍由本地规则引擎完成**（可复现、零幻觉）。

**为什么需要本机代理**：智谱 `open.bigmodel.cn` 不支持浏览器 CORS 直连——OPTIONS 预检不返回 `Access-Control-Allow-Origin`，浏览器会拦掉带 `Authorization` 的 POST。所以：

```
浏览器 → http://127.0.0.1:8787/api/chat（同源，无跨域）
       → server/dev.js 带密钥转发 → 智谱
```

- 本机开发：`node server/dev.js`，密钥放 `server/key.local.txt`（已 gitignore，**不进仓库、不进浏览器**）。
- GitHub 版：没有代理也没有密钥，`/api/chat` 404 → 自动降级为原文展示，**不报错**。用户可在「AI 设置」填自己的代理地址或支持跨域的服务商密钥。
- **`js/config.local.js` 只在 `localhost` / `127.0.0.1` / `file://` 下加载**（`index.html` 里用 `document.write` 判断后插入）。写死 `<script src>` 的话，GitHub Pages 每次访问都会在控制台留一个 404，破坏「零报错」这条验收线。
- 只对「异常影像项」调用（正常项不生成卡片，发了也是浪费）；结果随报告存盘，切成员/刷新不重复调用。
- 失败一律静默降级：`structurizeImaging` 返回 `null`，报告照常。
- 实测：`glm-4-flash` 抽两条影像描述约 **12.9s**，字段全对（`甲状腺/右叶/结节/2.4mm×1.7mm/边界清/无钙化`）。
